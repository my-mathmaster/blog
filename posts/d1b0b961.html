为一篇推理论文准备环境，为什么两步训练也折腾了这么久

发表于2026-11-02|更新于2026-11-02|LLM模型训练
|浏览量:

准备复现一篇大模型论文时，我们给自己定了一个很小的起点。先让一个公开模型读几道数学题，生成回答，更新两次参数，然后正常结束。如果这一圈跑通，再投入时间做正式训练和评测。

这个听起来只需要几分钟的小检查，最后经历了几轮排查。先是 GPU 初始化失败，接着是训练步数增加了、参数却没变化，好不容易看到真实更新，进程又在收尾时崩溃。最让人困惑的一次，训练已经结束，显存看起来还占着一大块。

事情起于《Self-Distilled Reasoner》这篇论文。它研究怎样让同一个语言模型给自己提供训练信号。学生只看到题目，教师还能看到参考解答。学生先生成自己的解题过程，再从教师那里获得逐步的训练指导。我们选择其中较小的 Qwen3-1.7B 开始，便于控制第一次验证的成本。论文与方法说明

论文还比较了 GRPO 这条强化学习基线。它对同一道题采样一组回答，按正确性打分，再根据组内的相对表现更新模型。我们先验证这条基线，希望确认生成、评分、反向传播和分布式更新都能走通。后面的自蒸馏实验有自己的训练目标和评测安排，需要继续单独验证。公开 GRPO 入口

做这种检查，很快就会遇到两个同时争用显存的角色。训练框架负责计算梯度和更新参数，vLLM 负责高效生成回答。这次采用共置方式，让它们在同一组 GPU 上轮流工作。驱动、深度学习框架、推理引擎和多卡通信都要配合，模型才有机会真正开始学习。

手里已经有一个 vLLM 镜像，所以最初从它开始盘点。镜像标签是 0.10.1，里面实际搭配的是 Python 3.12 和 Torch 2.7.1。容器启动时先被 CUDA 版本约束拦住，进入盘点环境后，GPU 初始化又返回了错误码 803。

这时只看镜像标签和宿主驱动版本，解释不了进程到底用了哪套库。我们在每一种启动环境下各起一个新进程，调用 CUDA 的初始化接口，再检查进程实际加载的驱动库文件。三次结果把问题缩小到了库的选择。

启动环境 实际加载的驱动库 初始化返回码
镜像默认环境 libcuda.so.570.124.06 803
取消 LD_LIBRARY_PATH libcuda.so.570.124.06 803
优先加载与宿主匹配的驱动库 libcuda.so.525.125.06 0

取消一个环境变量以后，进程仍然选中了同一个不匹配的库。让它实际加载匹配的库后，初始化才成功，随后浮点和 BF16 运算也通过了。这次排查让我更愿意先问一句，正在运行的进程到底加载了什么？

之后按公开仓库的依赖要求准备了独立环境。最后跑通的组合是 Python 3.10、Torch 2.8.0、vLLM 0.11.0 和 TRL 0.26.0，另外使用了 Transformers 4.57.1、DeepSpeed 0.18.2、FlashAttention 2.8.3。安装后先检查导入和依赖一致性，再检查单卡计算、CPU 优化器、多卡通信和小模型生成。每通过一层，才继续往完整训练入口走。仓库环境配置

第一版小检查刻意把预算压得很低。只训练两步，回答最多生成 256 tokens。token 是模型计算文本长度的单位。它确实很快走完了优化器计数，但这批回答全部被截断，组内优势全为零，抽查的参数也没有变化。

回头看，这是一个很容易漏掉的问题。对推理模型来说，一段解题过程可能已经写了几百个 token，最后答案还没出现。若一组回答得到相同的正确性奖励，GRPO 就没有组内相对差异可用。这时进度条走到了第二步，也不能说明我们观察到了有效更新。

于是我们保留两次优化更新，把生成长度恢复到论文 GRPO 配置允许的范围。题目最多 2,048 tokens，回答最多 16,000 tokens，每题采样 8 条，温度 1.2。num_iterations=2 让同一批生成结果用于两次更新。这样既能限制检查时长，也给模型留下了把题答完的机会。论文训练配置

实际可用的是七张卡，原启动示例按八卡组织全局批量。为了保留每题八条回答，并让各卡采用相同的整数分批方式，这次使用全局批量 56，论文中的对应值为 32。我们把这个差异写进结果里。数据来自公开数学训练集的八行真实题目，本次验收只覆盖这批数据上的两次更新。

回答能正常结束以后，我们终于看到了非零梯度和参数变化。随后却出现了更意外的情况。计算主体完成了，进程在退出时发生原生崩溃，日志指向 CUDA 内存池的析构。

当时为了节省显存，额外打开了 vLLM 的 sleep mode。它允许共置的推理引擎在暂时不用时释放或转移一部分显存，给训练阶段让出空间。这个功能也让资源管理更复杂了，退出时需要处理 Python 对象、模型张量以及底层分配器之间的生命周期。

生成时，引擎会把注意力计算中的一部分信息保存在 KV 缓存中，避免每一步都从头计算。排查中，这部分缓存的活动字节先降到了零，模型权重却仍然被引用。继续看源码，还发现这个版本的模型构造过程会为同一个实例注册两条编译回调。我们曾误以为只有一条，额外写出的数量断言因此又制造了一次失败。修正断言、注销回调之后，外层引擎对象已经回收，仍有权重张量存活。还有哪些对象持有它们，当时的证据没有完整定位出来。对应版本的编译回调源码

转折来自重新阅读原始配置。仓库的 GRPO 启动脚本没有开启 sleep mode，锁定的 TRL 版本默认值也是 False。在对应的 vLLM 实现里，开启它会让权重和 KV 缓存进入专用内存池。最终一轮恢复了这个默认配置，使用标准的引擎关闭和通信组销毁接口，再由外部监督进程确认真正的退出结果。TRL 默认配置 · vLLM 内存分配路径

关闭 sleep 以后，推理侧的 KV 缓存会在优化阶段继续占用显存，因此还要重新核算预算。我们保留每题 8 个回答，但让引擎每次最多同时处理 4 条，其余排队。根据公开模型结构计算，四条达到本次总长度上限的序列需要约 7.71 GiB 的 KV 缓存，放在每卡 8 GiB 的预算内。生成条数和同时生成的条数可以分别控制，这为长回答留下了空间。

最后一轮终于完整结束。从启动到完成约 8 分 37 秒，外部监督进程收到了下面这些结果。

观察对象 实测结果
多卡计算 七个训练进程都完成了启动通信校验，编译后正常计算
生成 56 条回答全部以结束标记 EOS 收尾，长度为 663 至 12,504 tokens
更新 每个进程完成 16 次小批量计算，累积梯度后执行两步优化，抽查的参数片段发生了变化
退出 七个训练进程的实际退出码全部为 0
显存 七张卡在进程退出后第一次采样时，全部回到开跑前的空闲基线，计算进程列表为空

其中最值得留下的观察发生在进程结束前后。进程内最后一次读取 PyTorch 计数器，每个进程仍有约 11.28 GiB 的已分配显存。等七个进程正常退出，外部采样已经全部回到了基线。在这个案例里，进程结束前看到张量还活着，不能单凭这个读数判断资源最终没有归还。

这也改变了我们给小检查收尾的方式。训练进程记录生成结果、梯度和参数变化，外部监督进程记录实际退出码、退出后的进程列表和显存。每次运行都留下独立结果，计算完成、异常终止和结果回传各有自己的状态。后来再判断一次检查是否通过，就能直接读到这些证据。

这次准备工作到这里告一段落。它已经证明这组公开模型和依赖能够完成七卡两步 GRPO，并在结束后交还显存。接下来的自蒸馏训练、长时间运行和数学榜单评测，还需要沿着同样的证据链继续做。
